编辑 | 玉澄

  “有时模型实际上能察觉到自己是在虚拟环境还是在真实环境中运行，这会导致它在强化学习（RL）期间的表现与在生产环境中的表现有所不同。”

  “模型简直太喜欢作弊了，强化学习非常擅长鼓励这种“作弊”行为。”

  不久前，Cursor 发布了其自有模型 Composer 的第二代最新版本，性能直逼 Claude Opus 4.7，而价格仅为其 1/10，在社区引起了一波轰动。

  一个应用层公司转变成为一家真正的前沿模型实验室，真的很好奇他们是如何做到。

  恰好近期，红衫官方播客邀请了 Cursor Composer 2 项目的研究负责人 Federico Cassano ，和负责为此项目提供分布式基础设施的 Fireworks 的 Dmytro Dzhulgakov，聊了聊“Composer 2 是如何被构建的”这个话题。

  我们这就来了解一下~

  在 5 月 19 日新模型发布时，官方提及在 Kimi K2.5 开源基础上，最新模型训练的 85% 算力花在了中期训练和强化学习上。这次的聊天基本上就是围绕着中期训练和强化学习来进行的。

  首先惊呆小编的一点是，Federico 说在 RL 过程中，如果模拟环境与真实的用户电脑环境稍有差异，模型是能察觉到自己正处于“虚假环境”中的。

  而当模型意识到这点后，它还会用一些“小花招”来“作弊”，以获得更高奖励值，而不是真正去学习解决问题的方法。

  在 RL 对模型的作用方面，Federico 的洞见也非常有趣。他说预训练是让模型吸收人类的全部知识，而 RL 阶段则像在调节一个“旋钮”，让模型明白“嘿，你是个专家，你需要把事情做正确。”

  并且在 RL 训练期间，模型会直接与 Cursor 的 Harness 进行交互，这让模型能够了解“自己余生将要生存的这个‘世界’”。

  Dmytro 也分享了一个对行外人士非常有冲击力的事实，那就是浮点运算在计算机上是非确定性的，即 a+b+c 的结果不一定等于 c+b+a。

  而这对 RL 影响很大，因为混合专家模型（MoE）对精度极度敏感，计算差异会导致模型激活完全不同的专家节点，产生完全不同的结果。

  因此，微小的计算差异是会导致 RL 训练失败的。所以为了解决这个问题，工程师需要手动编写复杂的 GPU 内核来强制运算顺序一致。

  在推理算力分配上，Federico 也有着独特的见解。他认为在推理上消耗的 FLOPs 远多于训练是一个迷思，理想情况下应该将 1/3 的 GPU 算力分配给推理，剩下的用于更新权重。

  另外，他们认为对于特定领域，模型的“专门化”胜过“通用化”。

  传统认为模型越大、越通用越好，但他们将所有模型权重针对“Cursor 内部的软件工程”任务专业化后，较小的模型能在性能上接近 Opus 这样的大模型，而且成本降低了一个数量级。

  此外，Harness 上也会跑 RL。通过对 Harness 的一部分与模型本身组成的系统进行 RL 优化，他们让 Composer 2 训练出了“自我总结”或“压缩”能力，而这能让模型在 20 万上下文窗口基础上实际处理百万个 Token。

  他还分享了自己对 RL 环境的理解。他认为 RL 环境实际上是由三部分组成，分别是 Harness、操作系统和奖励组件。

  其中 Harness 通常是可移植的，关键的是操作系统。所以在 Cursor，他们自己构建了具备极强爆发性的整个虚拟机栈（virtual machine stack），这样他们能够根据需求瞬间启动 10 万个虚拟机供模型进行实验。

  至于奖励组件呢，访谈中主持人有问到在 RL 中他们使用的是什么样的奖励信号？结果是不能说，“绝对机密”。

  还有一个问题他们也表示不能回答，就是对于Andre Karpathy 说过的：目前的 RL 仍然极其低效，进行一次漫长的“展开”（rollout），最后却只能在末尾得到一点点信息，这感觉就像是用吸管在吸取比特。他们对如何“从这条路径中榨取更多的比特”也是保密态度。

  成本低一个数量级！模型权重针对编程任务专业化

  主持人：今天很高兴能与两位聊聊 Composer 2 的训练是如何完成的，你们共同解决了哪些难题，以及你们认为这对 AI 和基座模型公司的未来意味着什么。

  Federico / Dmytro：听起来很让人兴奋。是的，很让人兴奋。谢谢你邀请我们。

  主持人：感谢你们的加入。对于那些没有密切关注我们的人，Cursor 最近发布了 Composer 2，这是一个专门用于长周期（long horizon）编码任务的智能体编码模型。Federico，在此之前，Cursor 主要是在赋能其他人的编码智能体。是什么促使 Cursor 如此大力地投入到 Composer 2 的研发中？对于你们来说，从一家单纯的应用层公司转型为一家同时拥有自己基座模型的公司，这具有多大的生死存亡意义？

  Federico：我们开始研究训练自己模型的原因是，你可以把模型看作是一种存储驱动器，它的权重中可以存储一定数量的比特。想法其实非常简单：我们只关心一项任务，我们甚至不一定关心广义的编码或编程，我们只关心 Cursor 内部的软件工程，而且仅限于 Cursor 内部。那么，如果我们把模型权重中能存储的所有信息比特，全部完全分配给这一项特定的任务会怎么样呢？此外，大家可能也注意到了，Composer 的成本比 Opus 和其他类似的编码模型要低一个数量级，因为我们只需将所有的模型权重针对该特定任务进行专业化，这样我们就可以提供一个更小的模型或类似的东西。

  Dmytro：是的。

  主持人：所以，核心在于确保我们拥有的每一个权重比特或信息，都专注于我们眼前要解决的特定问题。

  Federico：完全正确。

  主持人：明白了。这听起来像是一个几乎可以泛化的问题。Dmytro，我很想听听你的看法。你认为所有的应用层公司都应该把 Cursor 视为未来的风向标吗？他们是不是都应该尝试做同样的事情？

  Dmytro：是的，绝对应该。我的意思是，我们通常认为这是应用演进的一种普遍模式。你可能从做原型开始，使用一些现成的模型来让项目跑起来。你可能会做一些提示词工程，弄清楚你的 harness 是如何运作的。但是，你的应用中最具杠杆效应的属性，实际上是对用户数据的利用，或者应用运行方式的某些特定维度，比如你的框架的某些方面、你提供了哪些工具、应用是如何工作的，这些对你的应用来说至关重要。要捕捉到这些，通过提示词可以做到一点点，但真正正确的方法是打造一个完全在你的特定环境中运作的模型。

  Federico：是的，绝对是这样。比如智能体调用的某些工具，你很难用简短的语言向模型精确描述该工具的行为。而通过后训练，我们可以把使用这些工具的最佳方式直接烘焙进模型里。就像 Composer 一样，我们确实给 Composer 提供了一个提示词，但我认为以我们的训练方式，即使没有提示词它也能正常工作，它也会知道该怎么做。因为在整个训练过程中，我们本质上一直在把模型推向它应该表现的正确方向。

  Dmytro：提示词工程能达到的效果是有上限的。如果你想打造真正伟大的 AI 产品，你就必须经历微调（fine-tuning）并影响模型的行为，这是原因之一。第二个原因是成本和速度的权衡。我们在 Fireworks 的看法是，当你尝试进行优化时，你在质量、速度和成本之间面临着一个三维的权衡。最初，你仅靠优化基础设施就能走得挺远，我们和所有的客户一开始都是这么做的。但当你开始介入模型训练时，你真的可以把这种权衡推向更远，你可以用极低的成本、极快的运行速度获得更好的模型。Composer 就是一个很好的例子。

  主持人：关于这点我能进一步追问一下吗？我想问这种方法是否符合“苦涩的教训”（bitter lesson）这颗药丸的规律。在走进来之前，我们实际上都在聊 Tabnine（一款AI编程助手）。我记得在 LLM（大语言模型）时代到来之前，有很多这种小型的专业化编码模型。但让很多人感到惊讶的一点是，随着模型规模的扩大，你知道，仅仅通过在互联网、大量英文文本和其他语言上进行训练，模型本身在编码方面自然而然地也变得更好了。因此，至少到目前为止我看到的趋势是：更大的模型在所有事情上表现都更好，包括编码。你们所说的，是不是有悖于“苦涩的教训”的大趋势？

  Federico：我认为并没有。但有一点需要指出的是，各大实验室训练的大模型在代码数据上也投入了大量的训练。代码是实验室最想推进的核心任务之一，所以大模型并不只是自然泛化到编码的，它们本身也有一定的专业化。在我们的情况下，如果我们相信“苦涩的教训”，我们其实是在数据维度上大力推进。我们知道模型本质上容量是有限的，所以如果我们想饱和利用所有的容量，我们需要扩大数据规模。而为了注入更多的数据，我们需要让权重从模型可能受到的干扰中解放出来。

  主持人：明白，这非常有意思。好，让我们深入探讨一下 Composer 2 的训练。

  双轴训练赋能，RL 让模型更了解 Cursor 环境和写出正确的代码

  主持人：你们几周前发布了它，立刻吸引了全场的目光。强大的基准测试数据，推理运行成本也低得多。关于 Composer 2 是如何运作的，以及你们做了什么让它表现如此出色，能介绍一个精简版吗？

  Federico：我们是从一个非常强大的基础模型开始的，也就是 Kimi 2.5。那是一个总参数量 1 万亿、激活参数 30B 的模型，所以非常稀疏。实际上，我们审视了整个技术栈，意识到主要有两个轴。Composer 1 主要只在其中一个轴上发力，即强化学习（RL）；而 Composer 2 则在两个不同的轴上同时推进：一个是持续预训练，另一个是强化学习。让 Composer 2 变得非常优秀的原因正是双管齐下。我们在训练初期对代码 Token 进行了大量的“中期训练”，规模几乎接近预训练；然后在这段中期训练结束后，我们拿到了检查点，并在海量的任务上进行了非常大规模的强化学习。

  主持人：明白。这里的前提应该是，因为 Cursor 处于这么多有趣的编码 Token 的中心，你们拥有非常独特的数据访问优势，能够以几乎接近预训练的规模进行训练。

  Federico：是的。

  主持人：那为什么不直接预训练你们自己的模型呢？

  Federico：我们只是习惯自上而下、而不是自下而上地去思考我们的方法。换句话说，我们如何才能在最短的时间内，交付一个对用户有用的模型？如果我们从最底层开始，先去摸索怎么做预训练，然后把它扩大到中期训练，接着搞懂中期训练后再做强化学习，那要花很长很长的时间才能把模型交到用户手中。而通过反向操作，我们能够在极短的时间内给用户提供一个好用的模型。当然，我们希望接下来的 Composer 版本将会是我们自己的模型，而不是基于开源底座。

  主持人：明白了。那对你们来说，模型在中期训练阶段大概学到了什么？在后训练阶段又学到了什么？

  Federico：在中期训练中，它主要是学习各种代码库，以及非常常见的特定代码模式，同时也包含一些世界知识，其中也有网页数据。这实际上是在创造一个更广泛的分布，以便后续的强化学习可以在此基础上进行聚焦和提炼。在强化学习期间，模型可以直接与 Cursor 的 harness 进行交互。所以在某种程度上，它能够了解自己余生将要生存的这个“世界”，对吧？在强化学习中，它学会了如何正确调用工具、如何导航其所处的环境、如何编写正确的代码。因为在中期训练中，它只是学会了“如何写代码”，但这并不一定意味着它学会了“如何写出正确的代码”。我们虽然尽量用基本正确的代码进行训练，但模型本身并不知道如何区分正确与错误。而在 RL 阶段，我们做的核心事情之一就是微调模型的特性，告诉它：“嘿，现在你必须时刻写出正确的代码。”

  主持人：完全正确。

  Federico：很有意思。那在中期训练之后的这个模型，是类似于你们在 Tab 自动补全中使用的模型，还是属于不同的核心能力？

  Federico：是的，我的意思是……我想我会这样看：因为在中期训练期间，我们只是在做下一个 Token 的预测，也就是你预测下一个 Token 以及再下一个 Token 的准确度。

  主持人：既然如此，为什么不直接在你们的 Tab 自动补全模型上进行后训练呢？为什么要为不同的模型进行中期训练？

  Federico：因为 Tab 是一个非常小的模型，为了实现极低的延迟，它必须运行得非常快。所以这里基础模型有两个核心区别：Tab 非常小，而 Composer 相当大。

  RL 训练核心困境：会话展开、模型更新与算力利用率的多维权衡

  主持人：明白了，明白了。好。看来你们为 Composer 2 所做的大部分精力都集中在这次大规模强化学习的运行上。能帮我们拆解一下吗？这当中包含了什么，以及在此过程中你们解决了哪些不同的难题？

  Dmytro：当你做强化学习时，它与预训练或中期训练大不相同，因为你不仅仅是试图预测下一个 Token，你实际上是在运行整个框架，也就是整个实验。你在让模型在环境中行动，看它在特定“展开”（rollout）中的表现如何，“展开”就是这里的专业术语。并且根据它是否正确完成了某些事情来为它分配奖励，这可能是通过使用大模型（LLM）作为裁判，或者是一些可验证的指标，比如这段代码是否能成功编译。这意味着与常规训练相比，你需要大量其他组件：你仍然需要大规模训练，仍然需要编排成千上万个 GPU 来做正向和反向传播，做你在中期训练和预训练中做的一切事情；但现在你还需要编排一大堆环境，需要运行模型推理。因为当你进行这种“展开”时，你实际上是在运行一个真实的 Cursor 会话，对吧？

  主持人：抱歉打断一下，“展开”（rollout）基本上就是指来自 Cursor 的整个智能体历史会话，对吧？

  Dmytro：是的，这基本上意味着它可能需要进行 50 轮对话：模型接收初始提示词，然后决定调用一些工具，你要去执行这些工具，接着模型又生成一堆其他代码……这就是你与 Cursor 中的智能体互动时的完整会话。在训练运行中，你会把这整个会话模拟出来，得到最终的奖励，并利用该信号返回给训练器，将其融入到模型权重中。所以你拥有一个非常庞大的更新循环，而且它非常异构（heterogeneous），因为所有这些不同的组件都在协同工作。而现在你正试图编排这一切，让它高效、高吞吐量地运转，因为 GPU 非常昂贵，你希望以经济的方式快速训练好你的模型。

  所以这本身就是一个非常有趣的问题，处于算法和基础设施的交汇点，因为在系统如何进行共同优化和共同设计上存在着很多权衡。其中一个方面就是人们所说的“流水线异步化（asynchronous pipeline）”。其核心理念是，你试图分步更新这个模型：你拥有当前的模型版本，并试图用它进行大量的“展开”。那么在你进行这些“展开”时，你的训练器在做什么？一种朴素的方法会说：“好吧，现在我要停止我的训练器。我要去跑一堆会话”，而如果面对的是长周期任务，这些会话可能会运行 5 到 10 分钟甚至更长。“然后我拿到这些结果，暂停我的推理，回到训练中尝试进行更新。”这在理论算法上非常健壮，因为你没有产生任何偏差，但它在系统上非常低效，因为你有一半的算力一直处于闲置状态。所以作为替代，你可以使用所有这些聪明的算法技巧。

  主持人：是的。

  Dmytro：你可以把这一切都变成流水线。把这想象成一个巨大的工厂：你有一个训练器车间，还有一个“展开”车间，它们一直在旋转运转。进行“展开”的车间总是获取最新的模型版本并尝试跑新的会话，模拟新的智能体会话；而训练器车间则总是在新的结果一出来就拿过来，并尝试计算更新。所以一切都在马不停蹄地向前推进。这种权衡之所以在算法上有所不同，是因为当你完成模拟环境中的某些测试“展开”时，模型的权重可能已经在其他数据上更新过了。所以你会有这种陈旧性（staleness），也就是模型学习更新之间的延迟。因为当你处理完与模拟环境的某种交互会话时，你的模型已经改变了。这引入了有趣的训练动力学（training dynamics），有一些聪明的方法可以解决这个问题。但它的另一面是，你所有的 GPU、所有的计算资源都在时刻保持满载并高效运转，这意味着你在使用更多的每秒浮点运算（FLOPs）。回到你之前提到“苦涩的教训”的例子，这样就拥有了更高的计算效率。

  主持人：你可以在更短的时间内得到一个更好的模型。

  Dmytro：是的。也许你因为异步操作、没有进行完美的数学更新而损失了几个百分点的效果，但由于你没有把一半的算力闲置在那里，这极大地弥补了这一损失。这其中有很深的学问和有趣的交互。

  AI 也会“耍小聪明”！透露模型虚拟环境作弊现象

  Federico：我们在 Cursor 对性能是非常认真的，因为不像那些大实验室，我们只有几万张 GPU，而不是几百万张。所以，是的，我们用尽了各种招数来榨干 GPU 的每一点性能。比如我们在生产环境中甚至使用 FP4 进行训练；我们与 Fireworks 合作来推进推理性能。因为基础设施的特别之处在于，它本质上比预训练更复杂。因为你首先需要所有的预训练基础设施，这只是基本要求之一；然后，你需要所有的基础设施来运行这些环境，这些环境必须尽可能贴近地模拟用户电脑的实际情况。尽可能贴近是非常重要的，因为有时模型实际上能察觉到自己是在虚拟环境还是在真实环境中运行，这会导致它在强化学习期间的表现与在生产环境中的表现有所不同。

  主持人：你们有看到它意识到自己身处虚拟环境并开始表现得不一样吗？

  Federico：是的，确实有。

  主持人：真有意思。

  Federico：就像它会想：“哦，我在一个虚拟环境里。我学到了一些小花招，可以在这个环境里获得更高的奖励，让我来试试看。”模型简直太喜欢作弊了，强化学习（RL）非常擅长鼓励这种作弊行为。

  Federico：是的。而且我们还需要非常高效的推理，这至关重要。实际上存在一个迷思，认为在强化学习过程中，你在推理上消耗的 FLOPs 远多于训练。这其实只是因为开源推理引擎非常缺乏优化，而不是强化学习本身的特性。理论上它们的比例大致是相当的。如果把 GPU 的性能推到极限，你应该将大约三分之一的训练 GPU 分配给推理，对吧？因为训练实际上相当于三次正向传播：正向传播、数据梯度计算和权重梯度计算。而如果在推理时真正达到了临界批次大小（critical batch size），你只需要相当于单次正向传播的 FLOPs 消耗。

  主持人：所以这就是为什么你们选择使用 Fireworks，而不是使用开源推理引擎的原因。

  Federico：是的，我的意思是，另一种选择是我们自己内部研发一个，但像其他所有人一样，我们的工程师团队是有限的。我们更希望让工程师去提高训练的效率和精准度，而不是去单独开启一个推理引擎的研发项目。

  推理训练采取全球化分布部署，还抽调了部分生产算力

  主持人：明白，这太硬核了。另外，我记得你们在技术报告中提到，你们是以一种全球分布式的方式来做这件事的。为什么选择全球分布式？它的难点又在哪里？

  Federico：是的，原因有很多。首先，市场上很难找到非常巨大的单一连续集群。因此我们的做法是，用一个主要集群来运行所有的训练，毕竟我们无法建立一个全球化的训练集群；但是，我们可以把强化学习中的推理组件全球化分布式地部署到世界各地的小型集群中。在训练 Composer 2 时，我们总共使用了四个遍布全球且相距甚远的集群，我们甚至在生产流量处于低谷时利用了部分生产算力。比如当时我们正在服务上一代模型 Composer 1.5，当用户使用量最少的时候，我们就直接抽调一部分推理 GPU 来加速训练。通过这种方式，我们可以在没有单一连续大集群的情况下，轻松扩大训练规模。至于如何实现这一点，也许 Dmytro可以多讲讲。

  Dmytro：对，补充一下 Fed（Federico）所说的，我们的训练本质上是非常异构（heterogeneous）的。通过利用这种异构性，即不同组件对基础设施的不同需求，你实际上可以大幅提升效率，这种模式在各个地方都屡试不爽。具体来说，对于训练，你需要高度互联的集群、超高速网络，并且需要同步（lock-step）工作。因此这些集群非常昂贵，而且很难找到规模足够大的。

  基本上，在训练 Composer 的这种体量下，寻找一个两倍大的集群的难度，要远比寻找当前规模的集群大得多。这就是为什么如果你能把这些组件解耦（disaggregate）并部署在不同的地方，一方面你就不需要去找那么大的集群了；另一方面，你可以在硬件上做不同的权衡，因为推理不需要那么高的全局互联带宽，你只需要把较小规模的 GPU 互联在一起即可。你可以使用异构类型的 GPU，甚至不同世代的 GPU，在优化上玩出各种花样。最后，推理也更容易随着需求进行弹性伸缩。没错，在非高峰时段，你可以把整个推理资源池看作是一组既能为真实用户提供生产服务、又能为强化学习服务模拟环境的 GPU，并在两者之间取得平衡。当然，这是一个非常有趣的系统工程问题。

  一个 1TB 的训练步大约需要 5 到 15 分钟。这基本上意味着，每隔 5 到 10 分钟你就会产生一个全新的 1TB 模型权重快照（snapshot）。那么问题来了：你如何非常高效地把它传输到地球另一端的另一个集群？而且你必须动作飞快，因为前面提到过，你不能让这种数据陈旧性（staleness）失去控制。所以这可能是最有趣的部分，也是我们共同解决的问题，尽管整个模型有 1TB 大小，但并不是所有的权重在每一步都会发生变化。因为强化学习会进行许多非常精准的微调，特别是随着训练的进行。实际上，每次发生变化的权重子集存在着非常规律的模式，并不是所有权重每次都变。如果你去看模型在单次训练步（比如 10 分钟后）中的变化，它们之间的增量（delta）是相对较小的。因此你可以编写一个利用该特性的压缩算法，这样问题就变成了类似于数据库系统的问题：我拿到了这个增量，我只需要把它传输到世界各地。这个增量可能比传输整个模型要小 20 倍，这让方案变得切实可行。

  当然，现在你需要围绕存储系统构建起一整套机制。也就是完整快照、增量快照、恢复和对齐（reconciliation）等机制。我们成功以无损（lossless）的方式构建了它，这意味着传输到另一端的模型在比特级别上是完全等价的。所以你完全不用担心这当中会有任何差错，而且它的运行速度极快。即使在最糟糕的网络条件下，你也能在几分钟内完成传输，通常甚至不到一分钟。最重要的是，你只需要暂停大约 30 秒的时间，就能在实际推理中完成权重的切换。我们还通过对上传和下载进行分片（sharding），完全跑满了集群的出网带宽（egress）。所以你可以用所有设置系统层面的技巧来降低陈旧性。

  这确实相当复杂，但你可以把它抽象出来，让它完美运行，不干扰你的训练算法。反过来，你获得了这种解耦能力，可以借此利用其他集群来做这件事。这实际上颠覆了关于如何构建强化学习基础设施的传统认知。因为传统认知认为，你必须拥有一个通过 RDMA 互联的超大型集群，这极其昂贵，而且你可能需要分配三分之一的算力用于训练，三分之二用于推理。当然，如果你有非常昂贵的网络，快速复制这 1TB 数据确实更容易，但这意味着你需要一个三倍大的集群。现在，如果你的推理引擎更加优化，你无论如何都能在 GPU 数量上省去该集群三分之一的算力，因为效率更高了。而且你可以把这个集群的一半放到其他地方，使用其他地区更便宜的硬件，从而让成本大幅下降。

  浮点运算不确定性，成为 MoE 模型 RL 训练的致命隐患

  主持人：我特别喜欢你们在描述这一切时脸上的笑容，因为这真的太难了，这简直是系统工程师的梦想，对吧？你们构建的这套系统实在是太惊人了。

  Dmytro：为此我们熬了好多通宵。

  主持人：是的，看得出来你们在一起并肩作战了很久。说回正题，你在一开始提到过 Kimi 是一个非常庞大的稀疏模型。这会让强化学习的运行变得困难吗？具体是怎样的呢？

  Federico：当你做推理时，你本质上是在做一个自回归的正向传播。在这个正向传播中，它会产生它所采样 Token 的对数概率（log probabilities）。当我们把模型生成的这些样本送回训练器时，我们必须重新运行那次正向传播。因为如前所述，我们做的是异步训练，生成这些样本的模型版本实际上可能比训练器当前的进度落后了几步，所以我们必须重跑正向传播来重新计算对数概率。现在的难题是，理论上如果模型版本相同，这些对数概率应该完全一致。但即使是同一个模型版本，对于相同的 Token，你得到的对数概率值也会有轻微、甚至有时是非常显著的差异。这通常被称为推理的“数值不匹配”（numerical mismatch），现在在混合专家模型（MoE）中经常能听到这个词。

  主持人：这是为什么呢？为什么会发生这种情况？

  Dmytro：主要是因为从根本上说，模型所进行的浮点运算（floating point arithmetic）是具有不确定性（nondeterministic）的。

  主持人：抱歉打断一下，浮点运算是不确定的？

  Dmytro：对，我们在学校里学过，如果你计算a + b + c，或者计算c + b + a，结果应该是一样的。如果在计算机上用整数来做这个计算，这确实永远成立。

  Dmytro：但如果你用浮点数（它们实际上是近似值，包含尾数和指数等）来计算，a + b + c和c + b + a就会给你不同的结果。所以从根本上说，模型执行的所有操作基本上都是乘法和加法，而这些加法的累加顺序会影响最终的结果。这些都是微小的差异，但经过成千上万、甚至数十亿次的操作后，差异就会被放大。在对模型进行常规推理时，这通常没那么重要，因为经过预训练的模型本身鲁棒性很强，就算翻转几个比特，它依然能输出很好的结果，基准测试成绩也不会变。

  但在强化学习（RL）中，由于你是在用非常微弱的信号来教导模型，这种数值差异带来的噪声可以决定你训练的成败。这一点尤为重要。这再次成为算法和系统层面一个有趣的交汇点，因为你可以写出漂亮的数学公式，但在实践中它就是行不通。有一些方法可以将这种差异降到几乎为零，比如采用“批次不变”（batch-invariant）的方法，也就是非常小心地编写所有的 GPU 核函数（kernels），让它们始终按相同的顺序对数字进行加法，总是执行 a + b + c而不是其他顺序。这完全可行，但总会伴随着权衡，比如你的系统可能会变慢 2 到 3 倍。这就变成了一个有趣的权衡取舍：我们能接受多少性能损失？例如接受 10%（在实践中其实只要几个百分点）的降速，来解决 90% 的数值差异。这就是我们通过不断迭代共同找到的最佳权衡点。

  正如你提到的，稀疏性让这一切变得尤为困难。原因在于混合专家模型（MoE）的运作方式是：获取每一层的激活值（activations），并将它们送入一个门控层（gating layer）。门控层基本上决定了：对于当前这个 Token，我要从 384 个专家中选择哪 8 个来运行。它会进行一些数学计算，得分前 8 名的专家会被激活，其他专家则针对该 Token 保持闲置。这一操作会极大地放大微小的数值差异。因为可能你的隐藏状态（hidden states）只在小数点后第五位有极其微弱的差异，这本来无伤大雅，但这个差异偏偏导致它在截断时选择了 7 号专家而不是 9 号专家。结果，你突然激活了模型中完全不同的另一个部分，之前的差异被严重放大。

  因此，MoE 模型从定义上来说，对这种数值不匹配要敏感得多。当进行常规推理时，这通常无所谓，平均下来就相互抵消了。但现在如果你试图以此为基础让模型学习，这个差异就大得致命了。因为你在推理时激活的是 7 号专家，但在训练更新时，你却试图去更新那个在推理期间甚至根本没有做出贡献的 9 号专家。

  主持人：所以你们当时是靠手写 GPU 核函数来解决这个问题的吗？

  Dmytro：是的。你可以解决很多吞吐量方面的问题，这其中总是存在权衡。特别是针对 MoE，你可以使用一个被称为“路由器重放”（router replay）的有趣技巧。基本上，你可以让你的推理引擎向训练器传递一些额外的信息，比如告诉它：“嘿，我针对这个 Token 激活了 7 号专家。”这部分非常微小的信息只是一个整数，用以标明被激活的是哪个专家，这样训练器就可以与之保持对齐。许多数值对齐工作基本上都是在用类似的技巧，比如匹配量化级别、匹配核函数等，从而将训练与推理实现之间的分歧降到最低，这会带来巨大的改变。要么你的整个训练彻底发散，要么你因为需要多得多的数据去弥补这种不匹配而导致计算效率大幅下降。

  离线 RL 筑基，防止产生糟糕的用户体验

  主持人：我很想再多聊聊你们强化学习的具体方案。能透露一下你们使用的是什么样的奖励信号（reward signal）吗？或者不能说？好吧，不能说，明白了，机密内容，绝对机密。好，这可以理解。

  那既然在模拟环境中学习相当于进行模拟“展开”（rollout），而你们拥有如此庞大的真实用户数据可以用来学习，为什么不直接在真实的用户数据和真实的用户环境框架上做强化学习，而是非要在模拟环境中做呢？

  Federico：实际上我们也在这么做，这就是我们所说的“实时强化学习”（real-time RL）。我们使用相同的技术，通过 Fireworks 来实现推理权重的同步。我们会捕捉用户的信号，比如用户对模型某次生成的代码是满意还是失望，然后我们能够实时更新该模型，从而做到每隔几个小时就连续交付一个新版本的模型。我们正在努力缩短这个周期。不过实际上在未来的某个节点，我们必须再次延长这个周期，因为随着模型的上下文周期（horizon）变得越来越长，我们不得不重新拉长这个时间。这是一个有趣的博弈：眼下为了稳定性，我们正在努力缩短周期以摸索出正确的超参数；而在搞定超参数之后，为了进一步延长这些模型的长周期处理能力，我们又必须重新拉长这个时间。

  主持人：既然拥有这么多实际的用户数据，我心想这对于训练和微调来说肯定更有价值。那你们还需要做任何类似预训练阶段的模拟强化学习吗？为什么不直接进入在线强化学习（online RL）阶段？为什么还必须要做离线强化学习（offline RL）呢？

  Federico：目前的在线强化学习非常低效。我们面临的一个问题是，GPU 基本上会长时间处于“离线”闲置状态。除此之外，在效率和用户体验之间还存在着不同的权衡。如果你做模拟，你实际上可以针对同一个提示词（prompt）进行多次“展开”（rollouts）。也就是说，你拿一个任务，让模型尝试 16 次或者 128 次，从同一个提示词延伸出不同的展开路径。其中一些会进展顺利，另一些则不会。通过并行运行多个展开，你能够获得极其精准的信号。算法比如 GRPO（群体策略梯度）就是通过同时进行多个展开来运作的。而如果是在线运行，你每次只能收回一个展开信号，因此在算法实现上会有很大的权衡差异。最重要的一点是，如果模拟的展开搞砸了，那也没什么大不了的，最多只是浪费了一些 GPU 时间；但如果是面对真实的真实用户，你的准入门槛（minimum bar）要高得多，因为你实际上是在做 AB 测试，如果模型输出了奇奇怪怪的东西，那就是非常糟糕的用户体验。

  主持人：明白了，所以当面对的不是真实用户时，你可以更频繁地采用离线策略（off-policy），因为你可以尝试各种疯狂的想法而完全不用担心影响用户体验。你可以做更多次的展开，可以使用 GRPO，然后基本上可以把模型的性能引导（bootstrap）到一个足够好的水平，好到可以放到用户面前。

  Federico：没错，我们是通过离线（模拟）阶段来教会模型进行推理的。实际上，我们说的离线往往指类似 DPO 这样的技术，而 REINFORCE 这种更倾向于在线。在离线阶段，我们教模型如何推理，赋予它应当具备的行为模式。我们尝试给它注入关于这个世界的新信息，并教会它调用工具。之后，我们才会把它推上线面对用户。

  因为你可以想象，如果模型很糟糕，用户根本不会想去用它，也就不会给我们任何反馈，对吧？所以，模型必须达到一定的门槛，才能被引入到在线强化学习中。我们自己必须对模型非常满意，才会将其发布。这就是在线强化学习（或者我们喜欢称之为实时强化学习）的悖论所在：你无法用它来从头创建（create from scratch）一个模型，因为必须要先有用户去使用它。因此，它本身就必须已经足够优秀，我们只能通过在线方式让它变得更好。

  （注：DPO（Direct Preference Optimization，直接偏好优化） 是一种用于大型语言模型（LLM）对齐（Alignment） 的高效微调技术，主要目的是让模型的输出更符合人类的偏好（如更有帮助、更安全、更符合特定风格）。

  REINFORCE 是强化学习（Reinforcement Learning）中一种经典的**策略梯度（Policy Gradient）**算法，由 Ronald J. Williams 在 1992 年提出。 ）

  Federico：是的。这有点像锦上添花，真正为整个会话带来超级愉悦的体验。希望有一天，它能变成一颗巨大的樱桃。

  Dmytro：是的。

  主持人：是的。这让我想起 Dan Roberts 去年在我们大会上展示的内容，我想你当时也在场。传统上，它是大蛋糕和小樱桃的关系。

  Federico / Dmytro：现在是小蛋糕和大樱桃了。没错。

  Federico：呃，这个我不能透露。

  主持人：你提到每次“展开”需要几分钟的时间。目前似乎整个领域都在朝着打造“长周期智能体”（long horizon agents）的方向推进，即让智能体能够长时间不间断地工作，并且通常不会失败。我非常喜欢那个米级扩展图表（meter scaling chart）。在强化学习过程中，需要做些什么才能让智能体运行得更久呢？

  Federico：有几点。首先，强化学习的一个难点在于，执行轨迹（trajectory）越长，进行“信用分配”就越困难。你可以想象，我们是在模型结束全部工作后，才在最后给它一个赞或踩。简单来说，模型必须自问：“我哪里做对了，哪里做错了？”这就是所谓的信用分配问题。轨迹越长，这就越难。所以你必须在其中使用很多技巧。另一个问题是空间会不够用，这些模型的上下文窗口是有限的，迟早会达到上限。

  在 Cursor，我们解决这个问题的方法是在循环中加入“压缩”。我们称之为“自我总结”（self-summarization）。在强化学习过程中，智能体实际上学会了如何不断延续、永远进行下去。在实践中，我们的模型拥有 20 万的上下文窗口，但实际上它能处理数百万个 Token。这正是因为它有能力对自己的工作进行总结，然后利用这个总结重新启动它的上下文窗口，同时依然努力去完成既定任务。通过这种方式，我们在推动模型朝着目标正确行事的同时，也在共同训练模型生成高质量的摘要，并训练模型完美地理解该摘要。所以这几乎就像是推理能力的延续。

  Dmytro：我觉得这非常迷人。因为通常情况下，上下文管理被认为是 harness 的一部分，对吧？但在这种情况下，你们实际上是在协同优化 harness 的一部分与模型本身的工作，把所有这些都丢进了优化循环中。我们在 AI 领域一再看到，你往一个问题上投入的计算量越多，就越能端到端地解决这个问题。“苦涩的教训”（bitter lesson）中计算的魔力再次奏效，让你得到了一个能更好协同工作的系统。

  主持人：完全正确。你认为每家公司都会在自己的 harness 上跑 RL 吗？你认为每家公司面临的问题形式都和 Cursor 一样吗？

  Federico：如果他们正在使用 AI，并且正在生成大量的 Token，同时有一个可以优化的产品，我认为训练自己的模型就是正确的举措，也是正确的方向。

  主持人：明白，这很有意思。

  RL 让模型知道自己的角色是专家，需要把事情做正确

  主持人：所以，看起来你们做的大部分强化学习都集中在 harness 和工具使用这部分，而不是让模型变得擅长“预测代码的下一个 Token”。对于其他正在思考“我应该在哪里使用强化学习”的创始人来说，这大致就是他们应该参考的模式吗？也就是说：如果你想让智能体在长周期内使用工具执行任务，你需要强化学习。如果你只是想创建一个擅长总结或下一个 Token 预测之类的模型，你可能不需要强化学习。这是一个判断是否需要强化学习的好框架吗？

  Federico：我认为强化学习适用于任何地方。甚至对于 Tab 自动补全，我们也使用了……当然这只是我个人的理论，没有任何依据。当你预训练一个模型时，模型只是在吸收人类知识的全部集合。假设你正在训练一个数学模型，模型会学到 Stack Exchange 上所有的数学知识。当这个还没经过强化学习的模型面对一个数学问题时，它需要琢磨自己到底扮演的是什么角色，它是一个专家，还是一个试图学习的学生？因此，我认为在强化学习期间发生的事情之一，就是我们在调节这个旋钮，让模型知道：“嘿，你是个专家，你需要把事情做正确。”所以其中一个变化就是我们在提炼这种分布，这大概分为几个阶段。在第一阶段，模型学得非常快，很快就会变得很厉害；然后是第二阶段，需要耗费大量的计算量来持续提升模型，你会看到模型开始展现出推理能力并呈现出这种模式。在曲线的第一阶段，我认为我们只是在调节旋钮，告诉模型：“嘿，你在这里得把事情做对。”因此，在计算量较小的场景下，让模型知道它必须把事情做正确，也是非常有用的。这就是我的观点。

  （注：Stack Exchange 是一个由多个专业问答（Q&A）社区组成的网络平台，每个站点专注于一个特定领域，用户通过提问、回答和投票来分享高质量知识。）

  Dmytro：我非常赞同。我们在很多使用场景中都看到了这种模式。我们帮助很多客户进行过强化学习微调，通常你会发现，持续预训练（基本上是中期训练）和常规的监督微调（SFT），从抽象意义上说，更像是新知识的传递；而强化学习则是在提炼行为，或者说提炼你希望模型具备的特定品质。通常你两者都需要。甚至以你刚才提到的总结为例，强化学习在这方面其实也非常有用。因为有时候如果你想要某种特定风格的总结，你很难拿出完美的“好总结”和“坏总结”示例来精确描述它。但如果你使用大模型作为裁判（LLM as a judge），你实际上可以设定非常精准的评审标准。你可以通过提示词说：“好，这是我评估总结好坏的标准”，然后把它丢进强化学习循环中，让模型自己去尝试不同的总结风格，摸索出你到底想要什么，同时让另一个大模型去评估它是否符合特定的标准。这种模式你不仅在编码中能经常看到，在其他领域也屡见不爽。

  用大模型作为裁判，软件编写第三阶段：“编写评估规则”

  主持人：好，我要把下一个问题抛给Dmytro，因为 Federico 肯定会主张宪法第五修正案（选择保持沉默）。你刚才提到了好几次“大模型作为裁判”。你认为最终那些让专家手动检查 RL 展开路径、并以某种方式手动指导模型行为的公司会更成功，还是大模型作为裁判以及其他自动化评审标准更有可能带我们达到目标？

  Dmytro：你不可能真的让专家直接去评审每一次的展开路径。我的意思是，那就会变成某种……如果是真实用户的话，那就是实时强化学习，或者某种形式的 RLAIF（基于 AI 反馈的强化学习）或 DPO。总的来说，你的奖励信号越可验证（verifiable）越好，因为这能让你扩大计算规模，并在某些情况下获得更好的结果。所谓“可验证”，基本上意味着：你能在没有人类介入的情况下自动产生这个信号吗？当然，如果是数学或编码，你能设计出某种非常确定性的东西，那是最好的。大模型作为裁判之所以行得通，是因为它实际上属于“生成器与判别器”的区别，判断要比创造容易得多。对人类来说也是如此，对吧？当一个评判者要比当一个风投（VC）容易得多。

  主持人：哈哈，这里没有含沙射影的意思。

  Dmytro：确实没有别的意思。但确实，评判要容易得多，你可以精准地设计出你想要对某个回答进行排序的不同标准。你会看到这样一种模式：你可能会针对多个维度设计非常复杂的评估。因为如果你把多个维度一股脑丢给单个大模型，它可能会在如何评判上感到困惑，对吧？所以你可以把它拆解开来。比如：这个大模型根据风格进行评判，那个大模型根据不同的方面（如事实性）进行评判，从而真正打造出这些奖励信号。它们当中有些会是确定性的，有些会是基于大模型的，这就是引导你模型行为的东西。然后你只需投入更多的计算量，就能看到图表上的曲线一路走高。

  主持人：你认为我们会在那些更难验证的领域看到强化学习发挥更显著的作用吗？你认为大模型作为裁判足够应对吗？

  Dmytro：这是你会首先开始尝试的技术之一。理想情况下，你想弄清楚实际的结果是什么，你想获取的真实指标是什么。因此，尝试去逼近这个指标是一种方法，尝试去构建更大的模拟环境是另一种方法，对吧？如果你能模拟出更多你的产品，模拟出更多你的环境，你通常就能得到你所关心的最终指标，只是它更难被捕获而已。如果你能想出如何捕获它，那就太棒了。至于你行业专家的作用，专家依然是不可或缺的，因为设计这些任务并真正将产品体验编码进去，这才是至关重要的。我们经历了软件 1.0、2.0、3.0，对吧？过去我们是直接编写软件，后来我们转向编写训练数据，而现在，你实际上是在编写评估规则。但这依然非常重要。你需要看示例，看数据，看你的产品在哪里失败，以及如何引导模型走向正确的行为。

  RL 环境由三部分组成，Cursor 自己构建了整个虚拟机栈

  主持人：我想问问关于强化学习环境（RL environments）的问题，这可能与你刚才谈到的内容相关。现在似乎出现了一个大爆发，一些做 RL 环境的公司其营收规模正在急剧攀升。它们到底提供了什么真正有用的东西？因为我觉得以 Cursor 为例，你们已经拥有了关于客户实际上如何使用你们环境的海量数据。那么，强化学习环境供应商在你们已有的基础上，还能给你们提供什么呢？

  Federico：实际上我们没有使用任何环境供应商的产品。我认为构建一个能正常工作的环境是非常困难的。对于那些无法接触到这些数据的人来说，这是一个很有价值的产品。然而，特别是在编码领域，每个人都可以获得海量的可用编码环境。那就是 GitHub，对吧？你可以进去，让模型把一个仓库的所有依赖项全部安装好，这就是一个可以运行的环境。我认为很大一部分困难来自于基础设施。你可以想象，一个对特定任务有效的环境可能需要启动各种服务。比如你正在做一项修改，假设是一个数据库迁移，为了测试它是否真正起作用，你需要把数据库启动起来，对吧？这类事情是非常棘手的。我认为这些环境公司在这类事情上是挺有帮助的。

  Dmytro：这里面其实有两个层面。首先，如果你看前沿实验室，他们试图构建一个在所有事情上都很擅长的通用模型，所以他们需要涵盖所有这些不同的底层任务，打包进同一个模型中，并鼓励它去进行泛化。所以那是其中一个部分，在那种情况下它们非常有帮助。但如果是像 Composer 这样的情况，你拥有你真实的实际产品，我认为这也是我们在 Fireworks 所相信的，如果拥有自己的实际产品，你就应该针对它把效果做好。最强大的环境就是你自己的产品，完全正确。因为那是你的模型实际会被使用的地方。

  当然，如果你是前沿实验室，你不可能跨越所有的产品去做这件事；但如果你是想为自己的产品打造最好的模型，使其专业化并量身定制，你就应该直接使用你的生产环境（production environment）。当然，你需要对其进行妥善的隔离，对吧？你可不想让模型在你的生产数据库中大搞破坏，你需要进行克隆等操作。环境公司会提供一些工具，就像通用基础设施一样，让这一切变得更容易。但总的来说，你希望你的强化学习环境尽可能地接近真实的生产环境。

  举个例子，据我们所见，如果你去看那些玩具式的 RL 示例或玩具级框架，它们总是这样开始的：“哦，这里有一个玩具环境，我要启动一个 Docker 容器并在里面运行所有东西。”如果你只是想教模型怎么玩雅达利游戏之类的话，这确实很棒。但如果要真正过渡到生产案例，你不能只是把真实的生产应用塞进一个 Docker 容器里。我们自己很早就发现了这一点，比如和 MetaFox 合作时，在 Cursor 这边运行训练器。而对于其他一些客户，我们在我们的训练平台上运行训练器，但在环境方面，我们实际上默认在客户侧运行它们，因为那是实际实现所在的地方。你实际上拥有相同的训练器设置（即使它是 Fireworks 平台的一部分），在客户侧调用实际的生产环境，而不是试图去包裹它并将其组件化。

  Federico：在托管平台上做这个，因为那真的非常困难，而且会引入差异。

  我们所说的“强化学习环境”实际上由三个组件构成。第一是 harness，也就是模型可以提交工具、工具被执行的地方。第二是我们可以称之为“操作系统”的东西，也就是模型正在与之交互的实际世界和状态。第三是我们需要的奖励组件，它需要在最后检查工作是否正确完成。通常来说，harness 是相当可移植的，你可以把它带到许多不同的环境中。关键的部分是操作系统，而要复制这一点，普通的容器其实运行得不是很好。所以在 Cursor，我们实际上自己构建了整个虚拟机栈（virtual machine stack），这样我们就能非常快速地启动虚拟机。它必须具备极强的爆发性（bursty），因为你可以想象，我们可能会要求这个系统：“请现在给我提供 10 万台虚拟机”，然后它们必须全部启动完毕。
