我把 Codex 接进了扣子 3.0，搭了 Shopify 电商 Agent Team。

    

    👦🏻 作者: GaKi

    🥷 编辑: Koji

    🧑‍🎨 排版: NCon

   

   

   昨天，扣子正式升级到 3.0。

   「十字路口」团队第一时间做了实测，这次更新的内容还是比较多的——Agent Team 协作、本地 Agent 等多个能力同步上线，整体界面也做了重构。

   

   官方有一句很有「画面感」的介绍：在扣子 3.0 里，你可以组建一整个 Agent Team，@ 一下，全员就位。可以说，这是一次名副其实的大版本更新了。

   在展开 3.0 的细节之前，扣子这两年多的更新节奏，值得单独聊聊。

   2024 年 2 月 1 日，扣子国内版正式上线，当天流量爆表，服务器一度被挤垮。一年之后，2025 年 4 月，扣子空间推出，产品开始向个人工作场景延伸，邀请码一度刷屏。

   进入 2026 年，节奏明显加快。1 月 19 日，2.0 上线，核心是让 Agent 真正"能干活"，引入了长期计划与技能封装的概念；4 月 7 日，2.5 紧接着上线，给 Agent 配上了云电脑和云手机，让它能在真实系统环境里处理文件、操作 App；到了 5 月 25 日，3.0 进入内测，试图让多 Agent 协作体系落地。

   值得注意的是：

   2.0 到 2.5 之间隔了 78 天，而 2.5 到 3.0，只用了 48 天。

   先让 Agent 能干活，再给 Agent 配工具，最后让多个 Agent 互相配合是这几个多版本更新的基础逻辑线。

   先把产品推出去，跟着真实用户反馈持续校准，不死等所谓的「完美版本」。

   这种打法，非常「扣子」。

   🚥

   接下来，分享我们的完整实测体验。

   我把 Codex 接进了扣子 3.0，搭了 Shopify 电商 Agent Team

   这次更新涉及的内容比较多，我跑了一个相对完整的工作流去测，把这次更新到的功能基本都覆盖了一遍。

   这个案例本身对我也算是一个真实的工作需求，很多团队一直想做自己的周边电商，但内部并没有专职的选品、企划、外贸团队，这种情况下，能不能用一组 Agent 把前期的调研到 Shopify 店铺原型搭建这一段跑通，是我比较好奇的事。

   整体思路是：

   在扣子里组一个 Agent Team，上传「十字路口」的团队定位，让它先做小红书每日风向的调研、确定相关的风格元素，再进入外贸电商的选品调研，接着出商品企划，最后通过本地接入的 Codex，根据前面这一整套调研报告，快速搭出一个独立站的原型。

   整体看，扣子 3.0 这次界面做了重构，工作流的起点也从原来的对话形式，换成了以项目为单位。左上角可以直接新建一个项目，也可以先把要用到的 Agent 都建好。

   

   建 Agent 有两条路径，一种是新建云端 Agent，另一种是把本地的 Claude Code、Codex、OpenClaw 接进来。云端 Agent 的创建比较直接，写好名称就行。

   在我这个工作流里，先按节点把要做的事情拆开，大致分成：

   小红书风向标调研 Agent、外贸爆品调研 Agent、商品企划 Agent，再加一个由 Codex 组成的编程 Agent。

   在这几个子 Agent 之上，再设了一个主 Agent，负责统筹整个 Agent Team。

   这个拆法基本上就是主 Agent 相当于项目负责人，下面三个子 Agent 各管一个部分，编程 Agent 是网站原型快速落地的一环。

   

   每个 Agent 建出来之后，默认就带一组基础技能，需要的话可以再继续添加，模型是可以自定义的：

   

   在添加技能这一步，可以看到 Agent 市场里已经封装好的技能数量挺多的：

   

   需要哪一个就直接一键加上。比如小红书风向标调研 Agent 这条线，我给它配了热门账号推荐、爆款笔记、每日爆款笔记调研这几项。

   

   Agent 这一层整体上是好配的，配的时候你需要先把自己的工作流梳理一遍，按照节点对应去建 Agent，建好之后再统一组成一个项目。新建项目的界面比较简洁，直接勾选已经建好的 Agent，就能组成一个 Agent Team。

   

   我这个团队级的快速选品 Agent Team 里，设了一个项目总导演作为主 Agent，让它给下面的几个子 Agent 分工，按照外贸调研、商品企划、小红书爆款调研各自的职能去划分工作范围。

   

   分完工之后，主 Agent 会建议这三个子 Agent 同时开始各自的调研，最后由它来收口。

   

   确认完这一版 Plan，子 Agent 就开始各自在后台执行任务。

   

   每完成一个阶段，主 Agent 会轮询所有子 Agent 的执行情况。比如商品企划这条线先完成，给出了第一版 SKU 框架，里面分了 5 条产品线，每条产品线下有多个 SKU 角色，加起来一共几十个 SKU 候选。

   

   到这一步，可以一个一个去看子 Agent 的产出。商品企划 Agent 给到的是一份「十字路口周边商品矩阵」的调研报告，里面把各种款式都列了出来，比如引流款这条线下面的方向感珐琅徽章套装。

   报告本身支持导出成 PDF、Markdown、doc，也可以转成网页、播客或 PPT。

   

   产品线整体分了三档：基础款、传播款、高客单款。每一档都带一个参考价区间，背后也写明了核心定价逻辑。

   

   整份商品矩阵报告的颗粒度还可以，覆盖了用户调研、产品调研、客单价分析这几块。

   

   小红书爆款笔记调研 Agent 那边，主 Agent 给它的任务是去看小红书上的爆款笔记，整理这个方向的风向标。

   它会直接到小红书里去采集笔记，再结合我之前上传的团队定位，做一份小红书的周边趋势调研和视觉调研。

   

   这次我要做的是十字路口的周边，它会专门拆一些比较具体的点。比如周边的高频材质，亚克力、毛绒、贴纸、哑光纸盒等等，都被单独整理出来。

   

   这些调研内容是通过它身上挂的技能跑出来的。比如热门笔记的数据分析这一项，会按一组关键词去拉相关笔记，关键词覆盖了品牌周边、团队礼盒、员工礼物这一类高频场景。

   

   外贸爆品调研 Agent 这边，任务更具体一些，要围绕 POD 定制品做商品方向的调研，包括 Shopify、Amazon 上的强势品类。我在配置这个 Agent 的时候，给它挂了比较多的信息搜集和分析框架。

   

   比如它会直接进 Printful 2026，去看相关的基础款产品。

   

   接着按热度、视觉表现力、客单价、定制难度这几个维度给候选商品打分，输出一组比较细的商品候选类型。

   

   最后会给出方向性的建议，比如适合上哪些平台、哪些款不建议作为首批重压款，以及第一批上新组合应该长什么样：

   

   三条子 Agent 都跑完之后，主 Agent 把所有内容做综合汇总，给出第一阶段的方向建议，以及整个 AI 科技品牌周边的选品打样清单。

   

   接下来这一段我想单独拎出来讲，这是这次 3.0 一个比较关键的更新点：扣子现在支持接入本地 Agent，操作上只要一行命令。

   

   把命令复制到终端跑一下，会显示「已配对连接完成」。这一步本质上是去轮询你本地配置好的 CLI。我本地一共配了 Claude Code、Codex、OpenClaw 三个。

   

   再回到扣子 3.0 的页面，可以看到这几个本地 Agent 已经出现在可选列表里，勾选一下就能用。

   

   为什么单独提这一步：在生产级的工作流里，每个人都会有自己习惯用的 Agent CLI。我最近比较常用 Codex，对 Codex 的 harness 加 GPT-5.5 这一套搭配在编程上的表现比较认可，所以编程这一段我会留给本地 Codex 去做，而不是切到云端的某个 Agent。

   这种偏好的差异在以前不太好处理，要么只能用云端 Agent 产品，要么把整套工作流拆成两块，本地一块、平台一块，中间再手动接。现在直接接进来就行，本地的上下文也能被主 Agent 调度到，省掉了切窗口和复制粘贴的部分。

   接进来之后，一个比较直接的用途是快速做 Shopify 独立站原型。前面几条线的调研都汇总完了，可以让 Codex 直接照着这份汇总去出一个独立站的原型。下面这个就是这次做的 AI Cockpit 独立站原型，右侧是预留的商品卡片位置。

   

   商品列表这一段也能沿着上下文继续做下去。因为整个项目的上下文是打通的，从调研到原型，中间不需要再做一次信息搬运，迭代起来比较顺。

   

   跑下来，整个独立站原型的完成度还可以。

   

   需要补充的是，前面这一整套不只是 Web 端能用，手机端也是打通的，界面更紧凑一点：

   

   电脑上跑完之后，切到手机打开扣子 App，整个项目的对话记录、各个 Agent 的状态、任务的输出，全部都同步过来了。在手机上也可以继续推原型迭代，也就是常说的 Vibe Coding。

   如果发现某个地方不太对，可以直接在手机上 @ 主 Agent，也就是那个项目导演 Agent，让它再去调子 Agent 跑一轮更细致的逻辑迭代，比如某些 SKU 的 Brief：

   

   多 Agent 分工最明显的价值，是每件事都找到了更合适的处理方式。

   具体项目的 Coding 让 Codex 来做，实时检索让配了技能包的 Agent 来做，主 Agent 只负责统筹和整合。分开来，每个 Agent 在自己那件事上能做到 85 分左右。但全给一个通用 Agent 来全包，每件事可能都只有 70 分。这个差距在具体任务里感觉很明显。

   本地 Agent 接入这个设计，影响确实比较实际。

   我之前更偏爱的 Codex 接进来之后，扣子对我来说有了不同的用法：把已经在用的工具放进来，用扣子 3.0 去管理，不需要从头搭建一套「Agent 系统」，这本身也不好做。本地调试好的，不用重新搭，接进来就行。对有自己工具习惯的人来说，迁移成本低很多。

   扣子 3.0 具体效果如何，还是推荐大家亲自来玩一玩 ～
