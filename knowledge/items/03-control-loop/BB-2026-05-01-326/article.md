# Hello-Agents 地基参考：从智能体定义到记忆、上下文、协议与评估

## 1. 这份地基为什么重要

在研究 Claude Code 这种现代 coding agent 时，最容易掉进两个坑：

1. 只盯着产品表面功能，忽略背后的通用智能体结构；
2. 只看某篇逆向文章里的“内部实现细节”，却没有一套稳定的框架判断哪些是原理、哪些只是工程补丁。

`hello-agents` 恰好适合作为地基，因为它把智能体拆成了几块最关键的底层能力：

- 智能体定义与环境闭环
- 经典控制范式
- 记忆与检索
- 上下文工程
- 通信协议
- 性能评估

对我们后续理解 Claude Code 来说，这些内容的价值不在于“照着复现”，而在于提供一套通用坐标系。

---

## 2. 第一块地基：智能体不是聊天框，而是“感知-决策-行动”闭环

根据 `hello-agents` 第一章，智能体的最小定义包含四个要素：

- 环境（Environment）
- 传感器 / 输入（Sensors）
- 执行器 / 输出（Actuators）
- 为了目标做自主决策（Autonomy）

这一定义非常重要，因为它提醒我们：

> 智能体不是“会回答问题的模型”，而是“能够感知环境、基于内部状态做决策、并通过行动改变环境的实体”。

映射到 coding agent：

- 环境 = 代码库、终端、网络、Issue/PR、配置文件
- 传感器 = 文件读取、grep、搜索、日志、测试结果
- 执行器 = 写文件、跑命令、开子任务、提交代码
- 自主性 = 基于目标和上下文选择下一步动作

只要抓住这四点，就能快速看出 Claude Code 为什么不是普通 chat UI：它接入了真实工程环境，并且能对环境施加可验证的行动。

---

## 3. 第二块地基：控制循环决定 agent 的“做事方式”

`hello-agents` 第四章最有价值的部分，是把智能体工作流拆成几种经典范式。

### 3.1 ReAct：边想边做

ReAct 代表的是：

- 先思考当前最需要什么
- 调工具拿观察
- 再根据观察决定下一步
- 直到任务完成

这是大多数 coding agent 的基础骨架，因为真实代码任务往往无法一开始就规划得非常完整，必须边探索边推进。

### 3.2 Plan-and-Solve：先规划，再执行

Plan-and-Solve 更强调：

- 先把大任务拆成可执行步骤
- 再按计划逐步执行
- 在执行阶段维护状态

它适合较长、结构性更强的任务，比如跨多个模块的重构或多阶段交付。

### 3.3 Reflection：失败后反思与修正

Reflection 的核心是：

- 保留上一次尝试
- 对失败原因做回顾
- 生成下一轮更好的策略

这对应现实中的 coding agent 难题：第一次生成通常不够好，真正的能力来自“能不能用观察结果修正自己”。

### 3.4 对 Claude Code 的启发

Claude Code 的真正能力，并不在于单次答案多华丽，而在于它把这三类范式工程化地缝在了一起：

- ReAct：通过工具与代码库持续交互
- Plan：通过 plan mode、workflow、todo、task 分阶段推进
- Reflection：通过 review agent、hooks、任务恢复、上下文更新进行纠偏

所以，**看懂控制循环，才能看懂 Claude Code 为什么像一个“团队型工程体”而不是一个“高级补全器”。**

## 4. 第三块地基：记忆不是锦上添花，而是长任务必需品

`hello-agents` 第八章把记忆问题讲得很直白：如果 agent 不能记住过去交互，也不能从历史中提取可复用知识，那么它在连续对话和复杂任务里就会迅速退化。

它给出的几个关键启发是：

### 4.1 记忆需要分层

借鉴认知科学，可以把 agent 记忆至少理解成：

- 工作记忆：当前轮次与当前任务需要立即使用的信息
- 长期语义记忆：稳定知识、项目规范、领域事实
- 情景记忆：某次任务中发生过什么、之前踩过什么坑

### 4.2 RAG 不是唯一记忆

很多人一想到记忆就只想到向量数据库。但 `hello-agents` 的框架提醒我们：

- memory_tool 管交互与经验
- rag_tool 管知识检索
- 两者是并行协作而不是谁替代谁

### 4.3 对 Claude Code 的启发

用这个地基再看 Claude Code，就会发现它的“记忆”主要是外化工件：

- `CLAUDE.md`：项目级长期语义记忆
- skills / plugins / hooks：行为与规则记忆
- todo / task / workflow：任务级情景记忆
- transcript / logs / state：执行过程记忆

这比“模型自己记住”稳健得多，也更适合代码生产场景。

## 5. 第四块地基：上下文工程是智能体时代真正的工程主线

`hello-agents` 第九章非常关键，因为它把注意力从“提示词怎么写”提升到了“整个上下文如何管理”。

### 5.1 上下文工程不等于提示工程

提示工程关注的是：

- 怎么写 system prompt
- 怎么组织 few-shot
- 怎么描述任务

上下文工程关注的是更大的问题：

- 在一次模型调用前，到底应该给模型看哪些 tokens？
- 哪些信息该保留，哪些该裁剪？
- 长任务里如何持续地提炼上下文？

### 5.2 GSSC 流水线

Hello-Agents 把上下文构造抽象成一条 GSSC 流水线：

- Gather
- Select
- Structure
- Compress

这是一套非常适合用来分析 Claude Code 的方法，因为 Claude Code 的核心难题恰恰也是：

- 从代码库、任务历史、插件、工具、记忆中 gather 候选信息
- 选出当前步骤最相关的部分
- 组织成模型可消费的结构
- 在上下文预算下做压缩

### 5.3 NoteTool 与 TerminalTool 的启发

Hello-Agents 在第九章还强调两个能力：

- 结构化笔记：把状态和 blocker 外化
- 终端工具：即时探索真实文件系统，而不是预索引一切

这几乎就是现代 coding agent 的最小工作形态：

- 不预先吃完整个仓库
- 遇到问题再探索
- 发现有效信息后，沉淀为结构化记忆

这和 Claude Code 的真实实践非常一致。

## 6. 第五块地基：协议层让智能体不再困在单体工具箱里

`hello-agents` 第十章的意义在于把智能体通信从“写一个个 Tool 适配器”提升到“协议基础设施”。

它重点讲了三层：

### 6.1 MCP：模型到工具的标准化桥

MCP 解决的是：

- 工具如何统一暴露给模型
- 不同服务如何用统一方式接入
- 工具如何动态发现与调用

这让工具扩展从“每来一个服务就手写一个 adapter”转向“接协议即接能力”。

### 6.2 A2A：智能体到智能体的协作

A2A 解决的是：

- 一个 agent 如何调用另一个 agent
- 专家 agent 如何被协调者 agent 利用
- 多 agent 如何做点对点协同

### 6.3 ANP：更大规模网络化协作

ANP 关注的是：

- 服务发现
- 负载均衡
- 能力匹配
- 大规模 agent 网络中的调度

### 6.4 对 Claude Code 的启发

Claude Code 当前官方公开层已经明确支持：

- MCP servers
- specialized agents / subagents
- plugins / marketplace

这意味着它并不是孤立地在终端里做一轮轮问答，而是被设计成一个可以不断接入新能力、扩展新角色、组织新工作流的平台型 agent。

## 7. 第六块地基：没有评估，就没有可靠 agent

`hello-agents` 第十二章提醒我们一个很容易被忽略的问题：

> 智能体“看起来像会做事”，不等于它真的可靠。

评估至少要回答：

1. 它是否具备预期能力？
2. 在不同任务上表现如何？
3. 和其他方案相比怎么样？

### 7.1 为什么 agent 评估比普通软件测试更难

因为 agent 输出不是单一路径：

- 同一问题可能有多个正确答案
- 工具选择本身就是评估对象
- 多步任务的中间过程也可能出错
- 成本、延迟、正确率要一起看

### 7.2 评估不只是结果分数

Hello-Agents 提到的 benchmark 让我们意识到，agent 评估至少要覆盖：

- 工具调用是否正确
- 多步推理是否稳定
- 真实环境任务是否完成
- 多 agent 协作是否有效

### 7.3 对 Claude Code 的启发

因此分析 Claude Code 时，不能只问“它会不会写代码”，还要问：

- 大代码库里是否稳定？
- 长任务是否容易漂移？
- 子代理协作是否带来收益？
- hooks / permissions 是否减少事故？
- context / memory 是否真的降低重复成本？

这能帮助我们把关注点从 demo 成功率，转向 production-grade reliability。

## 8. 把六块地基拼起来：一套通用的 Claude Code 分析框架

如果把 `hello-agents` 的地基浓缩成一张分析表，它大概是这样：

| 地基模块 | 核心问题 | 观察 Claude Code 时看什么 |
| --- | --- | --- |
| 智能体定义 | 它如何感知、决策、行动？ | 文件读写、终端、网络、worktree、任务接口 |
| 控制循环 | 它怎么推进任务？ | plan、todo、workflow、subagents、review |
| 记忆 | 它怎么避免遗忘？ | `CLAUDE.md`、skills、task state、历史产物 |
| 上下文工程 | 它怎么控制 tokens 预算？ | 分层配置、即时探索、压缩与结构化 |
| 协议层 | 它怎么接外部能力？ | MCP、plugins、agents、marketplace |
| 评估 | 它怎么证明自己可靠？ | review、guardrails、monitor、benchmark 思维 |

这张表最大的好处是：

- 你不会把某个产品的特殊实现神化成原理；
- 你也不会因为只看功能表面，而忽略真正决定 agent 成败的宿主工程。

---

## 9. 一句话收束

如果说 Claude Code 是“生产级 coding agent 的一个具体产品答案”，那么 `hello-agents` 给我们的，就是理解这份答案所需的那套通用语法：

> 智能体 = 目标驱动的控制循环 + 可管理的上下文与记忆 + 可扩展的工具/协议层 + 可验证的评估与守护栏。

有了这套地基，再去看 Claude Code 的插件、任务、子代理、权限、上下文与恢复机制，就不会只看到零散功能，而能看到它作为一个完整 agent runtime 的骨架。
